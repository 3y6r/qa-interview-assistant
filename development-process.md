# Development Process

## 1. Назначение документа

Данный документ описывает процесс командной разработки проекта **QA Interview Assistant**.

Документ фиксирует правила работы с задачами, ветками, Pull Request, Code Review и статусами на доске Trello. Все участники команды должны придерживаться этих правил при выполнении задач проекта.

---

## 2. Основные ветки проекта

В проекте используются следующие основные ветки:

### main

Стабильная ветка проекта.

Ветка `main` используется для хранения проверенной версии приложения. Напрямую в `main` изменения не вносятся.

Правила для `main`:

* прямой push в `main` запрещён;
* изменения попадают в `main` только после проверки;
* ветка используется для стабильной версии проекта;
* удаление ветки запрещено;
* force push запрещён.

### develop

Основная рабочая ветка разработки.

Ветка `develop` используется для объединения задач, которые прошли первичную проверку и готовы к дальнейшему тестированию.

Правила для `develop`:

* все feature-ветки создаются от `develop`;
* Pull Request создаётся в `develop`;
* после проверки задачи изменения объединяются в `develop`.

---

## 3. Правила именования веток

Для каждой задачи создаётся отдельная ветка.

Формат ветки для новой функциональности:

```text
feature/PB-X-short-name
```

где:

* `PB-X` — номер задачи из Product Backlog;
* `short-name` — краткое название задачи на английском языке.

Примеры:

```text
feature/PB-3-project-structure
feature/PB-7-postgresql
feature/PB-11-workspace-screen
feature/PB-16-question-entity
```

Формат ветки для исправления ошибок:

```text
bugfix/PB-X-short-name
```

Примеры:

```text
bugfix/PB-3-cors-error
bugfix/PB-18-question-table-layout
```

---

## 4. Правила работы с Trello

Задачи ведутся на доске Trello.

Используются следующие колонки:

### Нужно сделать

В этой колонке находятся задачи, которые запланированы, но ещё не взяты в работу.

### В процессе

В эту колонку задача переносится, когда исполнитель начал работу.

Перед переносом задачи в эту колонку необходимо:

* назначить ответственного;
* проверить описание задачи;
* проверить чек-лист;
* убедиться, что задача понятна исполнителю.

### Готово

В эту колонку задача переносится только после выполнения всех обязательных условий:

* выполнен чек-лист задачи;
* результат загружен в GitHub;
* Pull Request создан и проверен;
* при необходимости задача проверена QA Engineer;
* критических замечаний нет.

---

## 5. Правила оформления карточек Trello

Каждая карточка должна быть связана с задачей Product Backlog.

Формат названия карточки:

```text
[PB-X] Название задачи
```

Примеры:

```text
[PB-1] Создание репозитория проекта
[PB-2] Настройка процесса разработки
[PB-3] Создание структуры проекта
```

В карточке должны быть указаны:

* описание задачи;
* ожидаемый результат при необходимости;
* участники;
* чек-лист;


---

## 6. Правила Pull Request

Все изменения должны проходить через Pull Request.

Pull Request создаётся из feature-ветки в `develop`.

Формат названия Pull Request:

```text
[PB-X] Краткое описание задачи
```

Примеры:

```text
[PB-2] Add development process
[PB-3] Create backend project structure
[PB-7] Configure PostgreSQL
```

В описании Pull Request нужно указать:

```text
Что сделано:
-

Как проверить:
-

Связанная карточка Trello:
-

Чек-лист:
- [ ] Код запускается локально
- [ ] Нет лишних файлов
- [ ] Изменения соответствуют задаче
- [ ] Документация обновлена при необходимости
- [ ] Задача готова к проверке
```

---

## 7. Правила Code Review

Code Review проводится перед объединением Pull Request.

Проверяющий должен убедиться, что:

* изменения соответствуют задаче;
* код не содержит лишних файлов;
* структура проекта не нарушена;
* код можно запустить локально;
* нет очевидных ошибок;
* при необходимости обновлена документация.

Если есть замечания, Pull Request возвращается исполнителю на доработку.

Если замечаний нет, Pull Request может быть объединён в `develop`.

---

## 8. Правила коммитов

Коммиты должны быть понятными и связанными с номером задачи.

Формат сообщения коммита:

```text
[PB-X] Краткое описание изменения
```

Примеры:

```text
[PB-2] Add development process
[PB-3] Add backend health endpoint
[PB-7] Configure database connection
```

Не рекомендуется использовать сообщения вида:

```text
fix
update
changes
test
123
```

---

## 9. Критерии готовности задачи

Задача считается выполненной, если:

* выполнен чек-лист в Trello;
* изменения внесены в отдельной ветке;
* создан Pull Request;
* Pull Request проверен другим участником команды;
* при необходимости QA Engineer выполнил проверку;
* критических дефектов нет;
* результат соответствует описанию задачи.

---

## 10. Ограничения текущего репозитория

Для ветки `main` создан ruleset `Protect main`.

GitHub показывает предупреждение, что ruleset не будет фактически применяться к private repository без GitHub Team organization. Поэтому ограничение фиксируется также как организационное правило команды:

* не пушить напрямую в `main`;
* не удалять `main`;
* не использовать force push;
* все изменения выполнять через Pull Request.

---

## 11. Ответственность участников

### Project Manager

* контролирует выполнение задач;
* следит за актуальностью Trello;
* распределяет задачи по участникам;
* проверяет готовность задач к демонстрации.

### Analyst

* описывает требования;
* уточняет Acceptance Criteria;
* следит за соответствием задач Vision & Scope;
* поддерживает документацию.

### Frontend Developer

* реализует пользовательский интерфейс;
* работает с React-приложением;
* подключает frontend к backend API.

### Backend Developer

* реализует серверную часть;
* работает с API, бизнес-логикой и базой данных;
* поддерживает структуру backend-проекта.

### DevOps

* отвечает за ветки, CI/CD, Docker и окружение;
* настраивает переменные окружения;
* помогает с запуском проекта.

### QA Engineer

* проверяет задачи;
* пишет тест-план и чек-листы;
* фиксирует дефекты;
* подтверждает готовность функциональности.

### QA/AI Engineer

* готовит AI-промпты;
* проверяет качество AI-черновиков вопросов;
* помогает наполнять базу вопросов тестовыми данными.
